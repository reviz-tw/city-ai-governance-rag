# RAG 效能與品質量測

每次串流問答會記錄 `context` 的 `latency_ms`、`rag_managed_search_ms`、`rag_legacy_search_ms`、`rag_search_ms`、`rag_preparation_ms`、`rag_first_text_ms`、`total_first_text_ms` 及 `rag_complete_ms`。這些是服務端計時，不含使用者建立新 session、網路或瀏覽器時間。完成才有 complete；失敗應另計失敗率，不能當成快速成功。日誌不輸出問題、回答或文件正文。

瀏覽器開發者工具的 `rag_client_timing_ms` 顯示從送出到來源、首字及結束的時間，包含建立新 session 的等待；不含問題或來源內容。這是本機診斷資訊，沒有自動上傳，無法直接當作全體使用者的分位數。

比較變更時應在相同文件版本、權限、部署和地區下重複測試，分開首輪與追問、冷啟動與暖機及並行負載，統計成功率以及來源、首字和完成時間的 p50／p95。記錄模型與設定、樣本數、時間與費用；不要把單次測試視為 p95。受控測試應避免將私人問題、證據或帳號寫入一般日誌。

同一題組應人工標記預期文件及段落，至少包含繁中、英文、日文、多語查詢、跨城市比較、追問、資料不足、私人文件及權限變化。比較前幾名的相關文件與段落、引用支持率、無資料時的表現及答案完整性；速度提升不能取代品質驗收。現有固定證據模型測試不衡量檢索召回。

查詢時 managed 與 legacy Search 並行，各自保持排序，再交錯並優先納入不同文件。這是多樣性啟發式，並非跨索引相關性分數校準；需以真實題組評估。任一搜尋失敗會明確回報搜尋不可用，不將錯誤當成無結果。空結果也不再自動下載原始 GCS 文件充當搜尋結果；舊 fallback 函式保留供其他維護用途，但不在問答路徑啟用。部署前應確認兩個索引均可用且 legacy 文件完整索引。

追問改寫只對狹義可辨識且未帶城市或主題範圍的獨立 AI 問題略過，其餘保留改寫；應持續以真實追問和多語題組檢查誤判。此文件描述量測方法，並不宣稱已取得新版本的線上 p95、品質比較或成本數字。
